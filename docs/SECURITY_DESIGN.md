# HYBRID-01 Security Design — Proposal

**Status:** design proposal; no cryptography has been implemented by this document. The first implementation should wait until the identity and key-verification decisions below are agreed and its cryptographic dependencies have been reviewed.

## 1. Security goals

1. A relay can store and forward a message without learning its body or SOS coordinates.
2. The intended recipient can verify the sender and detect message modification.
3. The sender can verify that a delivery receipt was generated by the intended recipient's app and refers to the exact message.
4. Replays and duplicate delivery do not create duplicate chat entries or receipts, including after an app restart.
5. Messaging remains entirely BLE/store-and-forward. Key verification and dashboard telemetry must not require internet access.
6. A dashboard or local telemetry bridge never receives plaintext, private keys, or message secrets.

These goals do **not** guarantee delivery. A malicious relay can drop, delay, or selectively forward traffic. BLE visibility and traffic analysis are not eliminated by message encryption.

## 2. Current security state

The current LinkMesh-derived protocol sends JSON messages with plaintext `content`, sender/recipient IDs, timestamps, hop fields, and (for SOS) coordinates. Device IDs are random identifiers, not cryptographic identities. ACKs are ordinary JSON messages; they are not signed. The relay queue is not encrypted at rest by the queue format itself.

Until the security work is implemented and tested, HYBRID-01 must describe messages as **unencrypted** and receipts as **unauthenticated**. The live demo should use non-sensitive sample text and locations.

## 3. Proposed trust and identity model

- Each installation has a persistent cryptographic identity key pair, separate from its display name and current UUID. A display name is a label, not proof of identity.
- Public keys may be exchanged over BLE, but that exchange alone is not trusted: a nearby attacker could substitute a key.
- For the showcase, explicitly verify and pin a peer's public-key fingerprint out of band—preferably by scanning a QR code in person and comparing a short fingerprint. Show `unverified` until this step is complete.
- Store private identity material using Android Keystore-backed protection. Key loss or device reset creates a new identity and requires peers to verify it again; do not silently treat a replacement key as the same person.
- No central server or account service is required.

**Selected default for HYBRID-01:** require in-person QR/fingerprint verification for demo peers. Until a fingerprint is confirmed, show the peer as `unverified`; BLE discovery alone must never imply identity. This is a deliberate, workable trust ceremony for a small presentation group.

## 4. Message protection and wire-format direction

Use a maintained, reviewed cryptographic protocol/library if one meets the offline, asynchronous, Flutter/Android, and licence requirements. Do not implement cipher primitives or a key-agreement protocol from scratch. If no suitable asynchronous protocol is available, document the reduced guarantees before choosing a simpler design.

The intended envelope has two layers:

### End-to-end protected payload

- Encrypt the message body and sensitive SOS fields for the intended recipient(s).
- Authenticate the sender and bind the ciphertext to immutable envelope fields: message ID, sender key ID, recipient key ID, message type, creation/expiry information, and ciphertext.
- Include a protocol version, algorithm/key identifiers, required ephemeral/prekey material, nonce, ciphertext, and authentication tag as required by the selected library.
- Never reuse an AEAD nonce with the same key. Let the selected protocol/library manage nonce and key derivation rules.

### Relay-visible routing metadata

The current flood router needs a destination to decide whether to deliver or forward. A first secure version may therefore expose sender/recipient identifiers, message ID, type, timestamps, and hop count to relays. Document this as metadata leakage. The relay must not need the plaintext body or location.

A relay may update `hop_count`, so that mutable field must not be included in a signature that relays would invalidate. The sender-authenticated fields and the relay-mutated fields must be clearly separated in the protocol. `max_hops` and expiry policy should be immutable and authenticated.

**Selected first-release scope:** secure one-to-one text only. SOS/group encryption is deferred until verified group membership, key distribution, member removal, and key rotation are designed. In the meantime, the app must warn that SOS content and coordinates are plaintext; never present SOS as encrypted.

## 5. Delivery receipts

A receipt should be a separately authenticated protocol message from the intended recipient. It should bind at least:

- the original message ID (`ref_id`),
- the recipient's verified identity/key ID,
- a unique receipt ID and protocol version,
- a receipt timestamp or expiry information.

The recipient should emit it only after successfully authenticating and storing the original message. Relays may forward it without being able to forge it. The original sender verifies the receipt against the recipient key it pinned.

The UI should label this state **delivered to the recipient app**. It does not prove a human read or understood the message, and a compromised recipient device can still lie.

## 6. Replay and duplicate handling

The current in-memory seen cache is not enough on its own. Maintain a persistent replay/deduplication ledger keyed by message ID (and receipt ID), with expiry at least as long as the accepted message lifetime. Queue state and replay history are distinct: removing a delivered message from the forwarding queue must not immediately make an old packet processable again.

- Insert the deduplication record before processing side effects.
- Keep recipient chat storage idempotent by message ID.
- On a duplicate after restart, do not create another chat entry or emit an unbounded stream of new receipts.
- Define bounded message size, queue size, hop limit, and expiry to reduce storage and flooding abuse.
- Do not rely on strict wall-clock ordering alone; offline phones may have inaccurate clocks.

## 7. Local data and observability

End-to-end encryption protects traffic from relays, but it does not automatically protect local chat history. Encrypt local message history at rest with a device-protected key before storing plaintext history in SQLite. The durable relay queue should store the encrypted envelope, not a plaintext copy of the body. Exclude secrets and private keys from logs, diagnostic events, and backups.

The dashboard event bridge may report event type, pseudonymous device/message IDs, timestamps, connection state, and whether an event is physical or simulated. It must not report message text, decrypted SOS coordinates, keys, or ciphertext unless a specific diagnostic need is approved. Telemetry remains optional and must not affect BLE delivery.

## 8. Threats and limits to communicate

**Addressed by the proposed design:** passive relays reading message bodies; undetected ciphertext modification; forged delivery receipts; duplicate processing after restart; key substitution after the peer has been verified out of band.

**Not solved automatically:** message dropping or delay, radio jamming, device seizure/unlocked-device access, traffic analysis, metadata exposure, denial of service, a compromised endpoint, or a user accepting the wrong fingerprint. Do not promise anonymity or guaranteed delivery.

## 9. Security acceptance tests

Before describing the secure mode as implemented, test that:

1. A relay can forward a queued message but cannot recover its plaintext or SOS coordinates.
2. The correct recipient decrypts; a wrong key fails closed.
3. Altered ciphertext or immutable authenticated fields are rejected.
4. An unverified/replaced public key is visibly untrusted and cannot silently inherit a peer identity.
5. A forged or mismatched receipt does not mark a message delivered; a valid recipient receipt does.
6. Replaying the same message/receipt before and after app restart produces one stored message and no receipt storm.
7. Restart and queue expiry preserve the agreed security behavior, while delivery remains independent of the dashboard and internet.
8. Local stored history is protected at rest, and diagnostics contain no plaintext or key material.

## 10. Initial library assessment

A source-level review of candidate repositories on 2026-11-16 found:

- [`dint-dev/cryptography`](https://github.com/dint-dev/cryptography) is Apache-2.0 licensed and its Dart package exposes primitives including X25519, Ed25519, AES-GCM, and HKDF. Its companion `cryptography_flutter` package uses platform APIs on Android. This is a plausible primitive provider, **not** a complete asynchronous messaging protocol; using it alone would leave us responsible for protocol composition, key lifecycle, and review.
- [`signalapp/libsignal`](https://github.com/signalapp/libsignal) contains the Signal Protocol and Double Ratchet, with Rust implementations exposed through Java, Swift, and TypeScript APIs. Its repository is AGPL-3.0, and its README says use outside Signal is unsupported. Android/Kotlin integration may be possible, but it adds JNI/Rust integration and distribution/licence obligations; it is not a drop-in Flutter protocol package.
- [`Nitish987/signal-protocol-dart-implementation`](https://github.com/Nitish987/signal-protocol-dart-implementation) describes itself as a Dart Signal implementation, but GitHub reports no repository licence and its latest repository update is 2024-12. Do not use it as a dependency without a licence and maintenance audit.

**Recommendation:** do not compose a home-grown protocol from primitives just to move quickly, and do not adopt an unlicensed clone. Before implementation, do a focused compatibility/licence review of using official libsignal through a small Android platform-channel layer versus finding another maintained, licensed implementation. If neither is suitable, keep the demo explicitly plaintext rather than claiming encryption.

## 11. Proposed implementation order

1. Keep the selected defaults: in-person QR/fingerprint verification, one-to-one secure text first, and receipts meaning “authenticated and stored by the recipient app.”
2. Finish the protocol/library compatibility and licence review; record the selected protocol and limitations.
3. Add versioned message-envelope and key-storage interfaces; keep the current plaintext mode visibly labelled as a development-only legacy mode.
4. Implement direct one-to-one protected messages and authenticated receipts, then test malformed, modified, wrong-key, and replay cases.
5. Add persistent replay history and protect local history/relay state.
6. Extend the selected design to SOS/group delivery only after key distribution and membership changes are defined.
7. Expose only privacy-reviewed security-state events to the dashboard.
